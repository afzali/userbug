# userbug

شبیه‌ساز کاربر برای تست اپ‌های وب. مثل یک کاربر واقعی قدم‌به‌قدم پیش می‌رود،
هم‌زمان **هرچه کاربر می‌بیند و هرچه سرور در لاگ می‌نویسد** را ثبت می‌کند، و هر
جا چیزی خراب شد آن را به‌شکل قابل بازتولید تحویل می‌دهد.

**راهنمای دستی: [GUIDE.md](GUIDE.md)** — چه اجرا کنید و کجا چه بنویسید.

## پیش‌نیاز: دو سرور بالا باشند

userbug هیچ اپی را بالا نمی‌آورد — فقط آدرس می‌گیرد. پس اول:

```bash
npm run dev
```

در پوشهٔ نپی (پورت ۵۱۷۳). و برای سناریوهایی که سمت سرور را می‌سنجند:

```bash
C:/xampp/php/php.exe -d log_errors=1 -d error_log=D:/Projects/nepi/nepi-data/php-error.log -S 127.0.0.1:8081 -t D:/Projects/nepi/server/public
```

هر دو به‌شکل پیکربندی در `.claude/launch.json` نپی هم هستند: `nepi-dev` و
`nepi-api-local`.

## رابط گرافیکی (فاز ۳)

در checkout تازه یک بار وابستگی‌ها را از ریشه نصب کنید؛ `postinstall` بستهٔ
مستقل `ui/` را هم دقیقاً از lockfile خودش نصب می‌کند:

```bash
npm install
```

برای بازسازی دستی همان dependencyها نیز `npm run ui:deps` در دسترس است. سپس
برای کار روزمره، رابط محلی را با یک دستور بسازید و باز کنید:

```bash
npm run ui
```

مرورگر خودکار روی `http://127.0.0.1:4174` باز می‌شود. رابط فقط روی loopback
گوش می‌دهد و احراز هویت ندارد؛ تاریخچه را مستقیماً از `runs/` می‌خواند و
وضعیت تریاژ را در فایل‌های `triage/` نگه می‌دارد.

از داخل رابط می‌توانید پروژه و سناریو را انتخاب و اجرا کنید، قدم/عکس/خطا را
زنده ببینید، کانفیگ و YAML را با اعتبارسنجی ویرایش کنید، یافته‌های تکراری را
تریاژ کنید، دو اجرا را مقایسه کنید و trace اصلی Playwright را در همان صفحه
باز کنید. برای توسعهٔ خود رابط:

```bash
npm run ui:dev
```

## اجرا

```bash
node bin/userbug.js run nepi
```

| دستور | کار |
|---|---|
| `run nepi` | همهٔ سناریوها |
| `run nepi --grep "دوبار کلیک"` | فیلتر روی **عنوان** سناریو |
| `run nepi --scenario scenarios/nepi` | فیلتر روی **مسیر فایل** |
| `run nepi --device "desktop,Pixel 7"` | ماتریس دستگاه — هر کدام یک اجرای جدا |
| `run nepi --headed` | مرورگر دیده شود |
| `run nepi --repeat 3` | هر سناریو سه بار (برای سنجیدن تکرارپذیری) |
| `list` | فهرست اجراهای گذشته |
| `report latest` | بازسازی گزارش از مخزن، **بدون اجرای دوباره** |
| `replay <runId> --only-findings` | همان هدف و دستگاه و سناریوها، دوباره |
| `diff <runA> <runB>` | چه یافته‌ای تازه است و چه یافته‌ای رفته |

`<runId>` می‌تواند `latest` یا پیشوندِ یکتا باشد.

## نتیجه چه می‌گوید

```
  قدم: 53  ·  یافتهٔ یکتا: 7  ·  خط لاگ سرور: 1
  8 failed
  2 passed
```

**«failed» یعنی یافته پیدا شد، نه اینکه ابزار خراب شده.** سناریویی که یافته
دارد قرمز می‌شود — این طراحی است. اگر همه‌چیز سبز بود، یعنی هیچ ایرادی پیدا
نشد.

هر یافته این شکلی است:

```
• [server] درخواست ثبت‌نام با فیلد نامعتبر — PHP Warning: Undefined variable $key» … (1×)
   ↑منبع     ↑قدم‌هایی که در آن‌ها دیده شد        ↑پیام                              ↑تکرار
```

منبع‌ها:

| منبع | یعنی |
|---|---|
| `console` | `console.error` یا promise رهاشده در مرورگر |
| `pageerror` | استثنای گرفته‌نشدهٔ جاوااسکریپت |
| `http` | پاسخ ۴xx یا ۵xx |
| `network` | درخواستی که اصلاً نرسید |
| `server` | خطی که **سرور** در لاگ نوشت، چسبیده به همان قدم |
| `blocker` | پنجره‌ای که روی مسیر کاربر نشسته و کلیک را می‌گرفت |
| `scenario` | سنجشِ `assert` که نخورد — یعنی خودِ سناریو تشخیص داد |
| `dialog` | `alert`/`confirm`/`prompt` |

**«خط لاگ سرور: 0» همیشه خوب نیست.** یعنی سرور در بازهٔ این اجرا چیزی ننوشت —
که یا چون سالم بوده، یا چون سناریو اصلاً به سرور نزده. گزارش HTML این را جدا
نشان می‌دهد.

عدد `(۳×)` تعداد تکرار است. یافته‌های هم‌اثرانگشت یکی می‌شوند و قدم‌هایی که در
آن‌ها دیده شده‌اند کنار هم می‌آیند — وگرنه یک باگ در پنجاه قدم، پنجاه ردیف
می‌شد.

## پوشهٔ `runs/`

هر اجرا یک پوشه با نام `<زمان>_<هدف>`. کل تاریخ روی دیسک می‌ماند و رابط
گرافیکی (فاز ۳) فقط از همین می‌خواند.

```
runs/2026-08-29T09-45-21_nepi/
  run.json         هدف، دستگاه، محیط، وضعیت، تعداد قدم و یافته، فهرست سناریوها
  events.ndjson    هر رخداد، خط‌به‌خط: خطای کلاینت، پاسخ شبکه، خط لاگ سرور، مرز قدم‌ها
  findings.ndjson  یافته‌ها با اثرانگشت، قدم، مسیر و جزئیات
  shots/           عکس پایانِ هر قدم، به ترتیب
  traces/          trace پلی‌رایت هر سناریو (رابط گرافیکی نمایشش می‌دهد)
  report.html      گزارش تک‌فایلی — همین را باز کنید
  junit.xml        همان نتیجه به زبان CI
```

`report.html` را از **همان پوشه** باز کنید تا عکس‌ها بیایند (مسیرشان نسبی است).

- `run.json` — `status: finished` یعنی گزارشگر کنار رفته بود (مثلاً با
  `--reporter=line`) ولی اجرا به‌درستی بسته شد. `passed`/`failed` یعنی
  گزارشگر هم بوده.
- `events.ndjson` — رکوردهایی با `kind: "step"` مرز قدم‌ها هستند: نام، زمان،
  عکس و تعداد خطا. بقیه رخدادِ خام‌اند.
- `findings.ndjson` — رکوردهای `synthetic: true` مالِ خودآزمای ابزارند و در
  گزارش جدا می‌آیند تا با یافته‌های واقعیِ پروژه قاطی نشوند.

پوشه در `.gitignore` است؛ اجراها محلی‌اند.

## CI

بدون رابط، بدون پرچم اضافه. هر اجرا کنار `report.html` یک `junit.xml` هم
می‌گذارد. برای اینکه CI فایل را جای ثابتی ببیند:

```bash
userbug run nepi --junit reports/userbug.xml
```

با `--device a,b` هر دستگاه فایل خودش را می‌گیرد
(`reports/userbug.desktop.xml` و `reports/userbug.Pixel-7.xml`) — وگرنه دستگاه
آخر بقیه را پاک می‌کرد.

کد خروج:

| کد | معنی |
|---|---|
| ۰ | هیچ یافته‌ای نبود |
| ۱ | یافته دارد |
| ۲ | خطای اجراگر یا کانفیگ — نتیجه قابل اتکا نیست |

**نگاشت به JUnit.** یک سناریو = یک `testcase`. یافتهٔ یکتا = `failure`. یعنی
سناریویی که سالم تمام شود ولی سه خطای کنسول بدهد، در CI شکست است — چون همان
چیزی است که این ابزار برایش ساخته شده. تستی که روی `expect` بشکند و هیچ
یافته‌ای ثبت نکند هم `failure` می‌گیرد؛ وضعیت واقعی تست‌ها از `traces.ndjson`
می‌آید.

اگر اجرا پیش از رسیدن به سناریو بشکند (دستگاه ناشناخته، کانفیگ خراب)، فایل
با یک `error` نوشته می‌شود، نه خالی. فایل بی‌`testcase` را بیشتر CIها سبز
می‌خوانند و «اجراگر نرسید» به «همه‌چیز سالم بود» ترجمه می‌شود.

`userbug report <runId> --junit <مسیر>` همین فایل را بدون اجرای دوباره
بازمی‌سازد. خروجی قطعی است: دو بار بازسازی، دو فایل یکسان.

## سناریوها

`scenarios/<هدف>/*.yml` — داده‌اند، نه کد. فرمتشان در
[scenarios/README.md](scenarios/README.md).

چند تا هنوز `.spec.js` هستند؛ دلیلش در
[scenarios/nepi/_migrated.md](scenarios/nepi/_migrated.md) نوشته شده.

`scenarios/_selftest/` خودآزمای ابزار است: عمداً خطا تزریق می‌کند تا مطمئن
شویم رصدگر خاموش نیست. «صفر خطا» وقتی ارزش دارد که بدانیم آشکارساز کار می‌کند.

**سناریوی هر هدف مالِ همان هدف است.** `scenarios/<هدف>/` — هم YAML و هم
`.spec.js` — فقط وقتی اجرا می‌شود که `<هدف>` همان هدفِ در دست باشد. بدون این،
وصل کردن پروژهٔ دوم سناریوهای پروژهٔ اول را با آدرس تازه اجرا می‌کرد و انبوهی
شکستِ بی‌معنا می‌داد.

## افزودن یک پروژهٔ تازه

یک فایل در `targets/`، بدون دست زدن به کد موتور:

```js
export default {
  name: 'my-app',
  baseURL: 'http://127.0.0.1:3000',
  environment: 'local',
};
```

بعد `scenarios/my-app/*.yml` بنویسید و `userbug run my-app` بزنید.

بقیهٔ کلیدها اختیاری‌اند و نبودشان قابلیت را خاموش می‌کند، نه اجرا را:

| کلید | نبودش یعنی |
|---|---|
| `logs` | لاگ سرور خوانده نمی‌شود |
| `apiURL` | فعل `request` روی این هدف کار نمی‌کند |
| `state.sql` | فعل `query` هم |
| `source` | مدل به سورس دسترسی ندارد |
| `isolation` | نه ریست، نه seed، نه ثبت‌نام — در گزارش `none` |

**حالت جعبه‌سیاه** همین است: هدفی که هیچ‌کدام را ندارد. آن‌وقت تنها لایهٔ رصد،
مرورگر است — خطای جاوااسکریپت، promise رهاشده، پاسخ ۴xx/۵xx و پنجرهٔ مزاحم. برای
سایتی که سورسش را نداریم، همین همه‌چیزِ ماست.

`targets/userbug-ui.config.js` نمونهٔ کامل همین حالت است: رابط گرافیکی خودِ
userbug به‌عنوان یک هدفِ بیرونی و بدون سورس.

## چند تصمیم که غافلگیر می‌کنند

**قرمز بودن، خبر خوب است.** فهرست یافته‌ها را بخوانید، نه رنگ را.

**یافته بدون بازتولید، یافته نیست.** سناریویی که با اپ مسابقه می‌دهد و گاهی
می‌برد، دور انداخته می‌شود و جایش سنجشِ قطعی می‌آید. `--repeat 3` همین را
می‌سنجد.

**allowlist باید کوتاه بماند.** فهرست بلند در `targets/nepi.config.js` یعنی
داریم مشکل را زیر فرش می‌کنیم.

**`seed.localStorage` باگ پنهان نمی‌کند.** مزاحمی که یافته‌اش قبلاً ثبت شده را
خاموش می‌کند تا بقیهٔ سناریوها را ناپایدار نکند — با کامنتی که می‌گوید با رفعِ
یافته باید برداشته شود.
