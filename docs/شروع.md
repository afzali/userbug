# از صفر تا اولین تست

راهنمای گام‌به‌گام. هر گام یک دستور است و می‌گوید چه باید ببینید.

> ## شما کد نمی‌نویسید
>
> فایل‌های تست را userbug می‌سازد. شما فقط دستور می‌زنید، در مرورگر کار
> می‌کنید، و انتخاب می‌کنید.
>
> اگر جایی در مستندات خطی مثل `import { test } from 'userbug/test'` دیدید،
> آن **داخلِ فایلِ تولیدشده** است، نه چیزی که باید تایپ کنید.
>
> بعداً اگر خواستید، همان فایل‌ها کدِ معمولیِ پلی‌رایت‌اند و می‌توانید دستی
> ویرایششان کنید — ولی لازم نیست.

`README.md` می‌گوید ابزار **چه** می‌کند؛ این فایل می‌گوید **چطور**.

---

## گام ۰ — اپِ خودتان را بالا بیاورید

userbug اپ را بالا نمی‌آورد؛ فقط به آدرسی اشاره می‌کند. این عمدی است: هر
پروژه با دستورِ خودش بالا می‌آید — با watch، پورت، و متغیرهای محیطیِ خودش،
گاهی در داکر — و ابزاری که بخواهد جایش تصمیم بگیرد یا اشتباه می‌کند یا
فهرستِ بی‌پایانی از حالت‌های خاص می‌شود.

```bash
cd <پروژهٔ شما>
npm run dev            # یا هر طور که همیشه بالایش می‌آورید
```

**بررسی:** آدرس را در مرورگر باز کنید و ببینید اپ می‌آید. اگر نه، بقیهٔ
گام‌ها بی‌معنا هستند.

---

## گام ۱ — userbug را آماده کنید

یک بار، در پوشهٔ خودِ userbug:

```bash
cd <مسیرِ userbug>
npm install
npx playwright install chromium
```

**بررسی:**

```bash
node bin/userbug.js help
```

باید راهنما را ببینید. اگر می‌خواهید همه‌جا `userbug` بنویسید به‌جای
`node bin/userbug.js`:

```bash
npm link
```

از این پس در این راهنما `userbug` نوشته می‌شود.

## گام ۲ — پروژه را معرفی کنید

```bash
userbug init myapp --base-url http://localhost:5173 --source <مسیرِ پروژه>
```

`myapp` نامی است که خودتان انتخاب می‌کنید؛ از این پس در همهٔ دستورها همان
را می‌آورید.

**بررسی:** فایلِ `targets/myapp.config.js` ساخته شده. بازش کنید و دو چیز
را کامل کنید:

```js
export default {
  baseURL: 'http://localhost:5173',
  apiURL: 'http://127.0.0.1:8081',     // اگر API جدا دارید
  environment: 'local',                 // دروازهٔ ایمنی — نبودش یعنی production

  logs: [                               // ← لاگ سرور
    { type: 'file', name: 'back', path: '${APP_ROOT}/logs/error.log' },
  ],

  source: { root: '${APP_ROOT}' },
};
```

سپس یک فایل `.env` کنارِ userbug بسازید:

```
APP_ROOT=D:/Projects/myapp
```

> **چرا `${APP_ROOT}` و نه مسیرِ مستقیم:** `.env` در گیت نیست، پس این
> کانفیگ روی ماشینِ بعدی و در CI هم کار می‌کند. مسیرِ مطلق هم کار می‌کند،
> ولی کانفیگ را به یک ماشین گره می‌زند.

> **چرا لاگ مهم است:** این تنها چیزی است که با پلی‌رایتِ خالی نمی‌شود.
> userbug مرزِ زمانیِ هر قدم را می‌گذارد، پس وقتی چیزی شکست معلوم است کدام
> خطِ لاگِ سرور مالِ کدام کنشِ کاربر بود.

## گام ۳ — پوشه را در ریپوی پروژه بسازید

```bash
userbug init myapp --workspace
```

**بررسی:** خروجی می‌گوید کجا ساخته شد و چه چیزی کامیت می‌شود. در پروژهٔ
شما این‌ها ساخته می‌شوند:

```
<پروژهٔ شما>/tests/userbug/
  playwright.config.js   تنظیمات از userbug می‌آید
  .gitignore             راز و نشستِ مرورگر را بیرون نگه می‌دارد
  .local/                همان‌ها
```

و می‌گوید در پروژه چه نصب کنید:

```bash
cd <پروژهٔ شما>
npm i -D "file:<مسیرِ userbug>"
```

**فقط همین یک بسته.**

> ⚠️ **`@playwright/test` را در پروژه نصب نکنید.** این نکته‌ای است که اگر
> ندانید ساعت‌ها می‌گیردتان.
>
> فایلِ تست `userbug/test` را وارد می‌کند و Node آن را از مسیرِ واقعیِ
> userbug حل می‌کند — یعنی fixtureها پلی‌رایتِ **userbug** را بار می‌کنند.
> اگر پروژه هم نسخهٔ خودش را داشته باشد و رانر از آنجا اجرا شود، دو نسخه
> در کار است و رانر تستی را که با نسخهٔ دیگر ساخته شده **اصلاً نمی‌بیند**.
> پیامش هم کمکی نمی‌کند: `No tests found`، در حالی که فایل سرِ جایش است.
>
> `userbug test` این را حل می‌کند: رانر از userbug، کانفیگ از پروژه.

**بررسی:**

```bash
cd <پروژهٔ شما>
node -e "import('userbug/test').then(m => console.log('OK', Object.keys(m)))"
```

باید `OK [ 'expect', 'test' ]` ببینید.

## گام ۴ — اولین تست را بسازید

دو راه. **گشت** برای وقتی که خودتان بلدید کجا بروید؛ **author** برای وقتی
که فقط می‌دانید چه می‌خواهید.

### راه الف — گشت (برای بارِ اول توصیه می‌شود)

```bash
userbug tour myapp
```

مرورگر باز می‌شود. **شما کار کنید** — وارد شوید، کلیک کنید، فرم پر کنید.
هرچه می‌کنید با توصیفِ معنایی ضبط می‌شود (نقش و برچسب، نه سلکتور)، پس
تغییرِ ساختارِ HTML بعداً تست را نمی‌شکند.

هم‌زمان در ترمینال حرف بزنید:

```
گشت> کتابخانهٔ کاربر                      این صفحه چیست
گشت> v مودالِ افزودن | اینجا فایل می‌گیرد    نامِ لایهٔ باز + توضیحش
گشت> n دکمهٔ بستن با Escape کار نمی‌کند       ایراد → یافتهٔ واقعی
گشت> q                                     پایان
```

**بررسی:** در پایان می‌گوید چند قدم ضبط شد و فایل کجا نوشته شد. بازش کنید
— عنوانِ بلوک‌ها از همان چیزی است که تایپ کردید:

```js
await ub.step('/contents — کتابخانهٔ کاربر', async () => { … });
```

### راه ب — از متن

```bash
userbug author myapp "وارد می‌شوم و اولین کتاب را باز می‌کنم"
```

بگویید کاربر **چه کاری می‌کند**، نه اینکه چه دکمه‌ای را بزند.

> هرچه `tour` و `learn` و `map` بیشتر رفته باشید، `author` دقیق‌تر است —
> چون از عنصرهای **واقعاً دیده‌شده** می‌سازد، نه از حدس.

## گام ۵ — اجرا کنید

```bash
userbug test myapp
```

**بررسی:** باید چیزی شبیه این ببینید:

```
Running 1 test using 1 worker
  ✓ ورود و افزودن کتاب (4.2s)
  1 passed
```

رایگان و بی‌مدل. این همان دستوری است که بعد از هر تغییرِ کد می‌زنید.

```bash
userbug test myapp --ui            # time-travel، watch mode، انتخاب سلکتور
userbug test myapp --headed        # مرورگر را ببینید
userbug test myapp --last-failed   # فقط آن‌هایی که شکستند
```

**اگر `ERR_CONNECTION_REFUSED` دیدید:** اپ خاموش است. برگردید به گام ۰.

## گام ۶ — ادعا اضافه کنید

**این مهم‌ترین گام است.** تستی که ادعا ندارد فقط می‌گوید «چیزی نشکست» —
اجرا می‌شود، سبز تمام می‌شود، و **هیچ‌چیز را نسنجیده**.

```bash
userbug expect myapp
```

بی `--from` فهرستِ تست‌ها را می‌دهد تا انتخاب کنید، بعد پیشنهادهایش را
شماره‌دار نشان می‌دهد:

```
    1. ? بعد از «زدنِ ورود»: کتابخانه باید دیده شود
         چون بعد از ورود کاربر به کتابخانه می‌رسد
    2. · در پایان: دکمهٔ «خروج» باید دیده شود
    3. ? در پایان: فرمِ ورود نباید دیده شود

  شماره‌ها را با ویرگول یا بازه بدهید — یا «همه» / «هیچ».
  کدام‌ها نوشته شوند؟ › ۲،۳
```

- `?` یعنی مدل خودش مطمئن نبوده
- ارقام و ویرگولِ فارسی هر دو کار می‌کنند
- **Enterِ خالی یعنی «کاری نکن»** — امن‌ترین پیش‌فرض وقتی قرار است فایلتان
  عوض شود

> **چرا انتخابِ جزئی:** مدل چهار ادعا می‌دهد و معمولاً دوتایش درست است.
> «همه یا هیچ» یعنی یا ادعای مشکوک را می‌پذیرید یا حرفِ درست را هم دور
> می‌ریزید.

ادعا **نرم** درج می‌شود: یافته ثبت می‌کند و اجرا ادامه می‌دهد. حرفِ
نیازمودهٔ مدل نباید بتواند بقیهٔ تست را از اجرا بیندازد. وقتی خودتان
تأییدش کردید، `--hard` سختش می‌کند و از آن به بعد یک قاعده است.

**بررسی:** دوباره `userbug test myapp` بزنید. حالا تست واقعاً چیزی را
می‌سنجد.

## کارهای روزمره

### بعد از هر تغییرِ کد

```bash
userbug impact myapp
```

```
  6 فایل از «HEAD» تا حالا عوض شده.
  3 تست در پوشهٔ پروژه.

  تست‌هایی که باید دوباره فکر شوند:
  · ورود و افزودن کتاب        /contents
  ? آشنایی با سامانه           /

  2 فایل به هیچ صفحه‌ای نگاشت نشد:
  ! src/lib/db/database.js
```

`?` یعنی شاهدش ضعیف است — صفحهٔ گذرگاهی که تقریباً هر تستی از آن رد
می‌شود. و آن فایل‌های نگاشت‌نشده مهم‌ترین بخشِ گزارش‌اند: عوض شده‌اند، به
همه‌جا اثر دارند، و «چیزی لازم نیست» دربارهٔ آن‌ها دروغِ آرام است.

### کشفِ خودکار

```bash
userbug map myapp --headed
```

خودش می‌گردد و نقشهٔ حالت‌ها را می‌سازد. `--headed` یعنی می‌بینیدش. و
حینش می‌توانید حرف بزنید:

```
n این مودال با Escape بسته نمی‌شود    یادداشت → یافته، با مسیرِ همان لحظه
w                                     الان کجاست؟
q                                     بس است — تمیز بایست
```

`q` قطعِ فوری نیست: خزش ممکن است وسطِ رندر باشد، پس در نخستین مرزِ امن
می‌ایستد و هرچه پیدا شده می‌ماند.

### شناختِ اپ

```bash
userbug learn myapp          # سورس را می‌خوانَد
userbug knowledge myapp      # چه می‌دانیم، و هر بند از کجا آمده
userbug capabilities myapp   # «این اپ چه دارد؟»
userbug coverage myapp       # «چه چیزی در سورس هست و صدایش نزده‌ایم»
```

هر بندِ شناخت با `by:` می‌گوید منبعش چه بوده — گشت، خزش، سورس، یا حرفِ
خودتان. حرفِ شما بر حدسِ ماشین می‌چربد.

### فایل‌های نمونه (برای تستِ آپلود)

```bash
userbug fixtures myapp --add ./نمونه.pdf --note "برای آزمونِ آپلودِ تکراری"
userbug fixtures myapp
```

تستِ آپلود از همین‌جا می‌خوانَد، نه از هر جای دیسک — پس تست به ماشینِ شما
گره نمی‌خورد.

## وقتی چیزی شکست

```bash
userbug test myapp --last-failed      # دوباره، فقط شکسته‌ها
```

و برای دیدنِ دقیقِ آنچه گذشت:

```bash
npx playwright show-trace <پروژه>/test-results/<نام>/trace.zip
```

اسنپ‌شاتِ DOM در هر قدم، نتورک، کنسول. و چون مرزِ زمانیِ هر قدم ثبت شده،
لاگِ سرور کنارِ همان قدمی می‌نشیند که شکست.

## چک‌لیستِ کوتاه

```bash
# یک بار
cd <userbug> && npm install && npx playwright install chromium && npm link
userbug init myapp --base-url <آدرس> --source <مسیرِ پروژه>
#   → targets/myapp.config.js را کامل کنید (لاگ‌ها) و .env بسازید
userbug init myapp --workspace
cd <پروژه> && npm i -D "file:<userbug>"

# هر تست
userbug tour myapp          # یا: userbug author myapp "<متن>"
userbug expect myapp        # ادعا اضافه کنید
userbug test myapp          # اجرا

# هر تغییرِ کد
userbug impact myapp
userbug test myapp
```

## نکته‌هایی که وقت‌تان را می‌گیرند اگر ندانید

**فارسی در ترمینال.** `cmd.exe` فارسی را جدا و وارونه نشان می‌دهد حتی با
`chcp 65001`. **Windows Terminal** درست نشان می‌دهد. اگر خروجی به‌هم‌ریخته
دیدید، اول ترمینال را عوض کنید نه کانفیگ را.

**اپ باید بالا باشد.** userbug بالا نمی‌آوردش.

**تستِ تازه ادعا ندارد، و این عمدی است.** کاوشگر نمی‌داند چه چیزی *باید*
می‌شد؛ ادعای حدسی یعنی باگِ امروز به‌عنوان «انتظارِ درست» رسمی شود.

**هزینهٔ مدل یک بار است.** `author`، `expect`، `learn` و `map` پول
می‌گیرند. `userbug test` رایگان است و هر بار که کد عوض شد اجرایش می‌کنید.

---

## چه چیزی هنوز نیست

`userbug quest` — کاوشِ هدف‌دار با مدل («برو ببین آپلودِ تکراری چه
می‌کند») — بسته است. قلبش با برداشتنِ اجرای YAML رفت و بازنویسی‌اش کارِ
مستقلی است. تا آن روز، `map` برای کشف و `tour` برای مسیرهای دقیق.
