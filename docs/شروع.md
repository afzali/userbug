# از صفر تا اولین تست

راهنمای عملی. هر قدم یک دستور است و می‌گوید چه انتظاری داشته باشید.

`README.md` می‌گوید ابزار **چه** می‌کند؛ این فایل می‌گوید **چطور**.

---

## پیش‌نیاز

اپِ شما باید بالا باشد. userbug اپ را بالا نمی‌آورد — فقط به آدرسی اشاره
می‌کند. این عمدی است: هر پروژه با دستورِ خودش بالا می‌آید، با watch و پورت
و متغیرهای محیطیِ خودش، و ابزاری که بخواهد جایش تصمیم بگیرد یا اشتباه
می‌کند یا فهرستِ بی‌پایانی از حالت‌های خاص می‌شود.

```bash
# در پوشهٔ اپِ خودتان، هر طور که همیشه بالایش می‌آورید
npm run dev
```

## قدم ۱ — پروژه را معرفی کنید

```bash
userbug init myapp --base-url http://localhost:5173 --source D:/Projects/myapp
```

یک `targets/myapp.config.js` ساخته می‌شود. بازش کنید و دو چیز را کامل کنید:

```js
export default {
  baseURL: 'http://localhost:5173',
  apiURL: 'http://127.0.0.1:8081',
  environment: 'local',          // دروازهٔ ایمنی — نبودش یعنی production

  logs: [                         // ← لاگ سرور، همان چیزی که پلی‌رایت نمی‌دهد
    { type: 'file', name: 'back', path: '${APP_ROOT}/logs/error.log' },
  ],

  source: { root: '${APP_ROOT}' },
};
```

`${APP_ROOT}` از `.env` خوانده می‌شود (`APP_ROOT=D:/Projects/myapp`). `.env`
در گیت نیست، پس این کانفیگ روی ماشینِ بعدی هم کار می‌کند.

> **چرا لاگ مهم است:** `ub.step()` مرزِ زمانیِ هر قدم را می‌گذارد، پس وقتی
> چیزی شکست معلوم است کدام خطِ لاگِ سرور مالِ کدام کنشِ کاربر بود. این تنها
> چیزی است که با پلی‌رایتِ خالی نمی‌شود.

## قدم ۲ — پوشه را در ریپوی پروژه بسازید

```bash
userbug init myapp --workspace
```

می‌سازد:

```
myapp/tests/userbug/
  playwright.config.js   تنظیمات از userbug می‌آید
  .gitignore             راز و نشستِ مرورگر را بیرون نگه می‌دارد
  .local/                همین‌ها
```

و می‌گوید در پروژه چه نصب کنید:

```bash
cd D:/Projects/myapp
npm i -D "file:D:/Projects/userbug"
```

همین. **`@playwright/test` را در پروژه نصب نکنید** — و این نکته‌ای است که
اگر ندانید ساعت‌ها می‌گیردتان.

> **چرا:** فایلِ تست `userbug/test` را وارد می‌کند، و Node آن را از مسیرِ
> واقعیِ userbug حل می‌کند. یعنی fixtureها پلی‌رایتِ **userbug** را بار
> می‌کنند. اگر رانر را از پروژه اجرا کنید، پلی‌رایتِ **پروژه** اجرا می‌شود
> و تستی که با نسخهٔ دیگری ساخته شده را اصلاً نمی‌بیند. پیامش هم کمکی
> نمی‌کند: `No tests found`، در حالی که فایل سرِ جایش است.
>
> پس یک نسخه: رانر از userbug، کانفیگ از پروژه. `userbug test` همین را
> می‌کند.

## قدم ۳ — اولین تست

دو راه دارید. **گشت** برای وقتی که خودتان بلدید کجا بروید؛ **author** برای
وقتی که فقط می‌دانید چه می‌خواهید.

### راه الف — گشت (توصیه می‌شود برای بارِ اول)

```bash
userbug tour myapp
```

مرورگر باز می‌شود. **شما کار کنید** — وارد شوید، کلیک کنید، فرم پر کنید.
هرچه می‌کنید با توصیفِ معنایی ضبط می‌شود (نقش و برچسب، نه سلکتور)، پس
تغییرِ ساختارِ HTML بعداً تست را نمی‌شکند.

هم‌زمان در ترمینال حرف بزنید:

```
گشت> کتابخانهٔ کاربر                     این صفحه چیست
گشت> v مودالِ افزودن | اینجا فایل می‌گیرد   نامِ لایهٔ باز + توضیحش
گشت> n دکمهٔ بستن با Escape کار نمی‌کند      ایراد → یافتهٔ واقعی
گشت> q                                    پایان
```

هرچه تایپ کنید **در عنوانِ بلوک‌های تست می‌نشیند**:

```js
await ub.step('/contents — کتابخانهٔ کاربر', async () => { … });
```

### راه ب — از متن

```bash
userbug author myapp "وارد می‌شوم و اولین کتاب را باز می‌کنم"
```

بگویید کاربر **چه کاری می‌کند**، نه اینکه چه دکمه‌ای را بزند. مدل از
شناختی که از اپ دارد قدم‌ها را می‌سازد.

> هرچه `tour` و `learn` و `map` بیشتر رفته باشید، `author` دقیق‌تر است —
> چون از عنصرهای **واقعاً دیده‌شده** می‌سازد، نه از حدس.

## قدم ۴ — اجرا

```bash
userbug test myapp
```

```
Running 1 test using 1 worker
  ✓ ورود و افزودن کتاب (4.2s)
  1 passed
```

رایگان و بی‌مدل. این همان دستوری است که بعد از هر تغییرِ کد می‌زنید.

```bash
userbug test myapp --ui            # time-travel، watch mode، انتخاب سلکتور
userbug test myapp --headed        # مرورگر را ببینید
userbug test myapp --last-failed   # فقط آن‌هایی که شکستند
```

## قدم ۵ — ادعا اضافه کنید

**این مهم‌ترین قدم است.** تستی که ادعا ندارد فقط می‌گوید «چیزی نشکست» —
اجرا می‌شود، سبز تمام می‌شود، و **هیچ‌چیز را نسنجیده**.

```bash
userbug expect myapp --list                    # عنصرهای واقعی — رایگان
userbug expect myapp --from ورود.spec.js        # پیشنهاد
userbug expect myapp --from ورود.spec.js --apply
```

مدل ادعا **نمی‌سازد، انتخاب می‌کند** — از عنصرهایی که در گشت یا خزش واقعاً
دیده شده‌اند. ادعایی که به عنصرِ خیالی اشاره کند، تستی می‌سازد که برای
همیشه قرمز است، و آدم یاد می‌گیرد قرمزها را نادیده بگیرد.

پیشنهاد **نرم** درج می‌شود:

```js
await expect.soft(locator, 'چرا').toBeVisible();   // یافته ثبت، اجرا ادامه
```

وقتی خودتان تأییدش کردید، `--hard` سختش می‌کند و از آن به بعد یک قاعده
است. حرفِ نیازمودهٔ مدل نباید بتواند بقیهٔ تست را از اجرا بیندازد.

## کارهای روزمره

### بعد از هر تغییرِ کد

```bash
userbug impact myapp
```

```
  6 فایل از «HEAD» تا حالا عوض شده.
  3 تست در پوشهٔ پروژه.

  تست‌هایی که باید دوباره فکر شوند:
  · ورود و افزودن کتاب        /contents
  ? آشنایی با سامانه           /

  2 فایل به هیچ صفحه‌ای نگاشت نشد:
  ! src/lib/db/database.js
```

`?` یعنی شاهدش ضعیف است — صفحهٔ گذرگاهی که تقریباً هر تستی از آن رد
می‌شود. و آن دو فایلِ نگاشت‌نشده مهم‌ترین بخشِ گزارش‌اند: عوض شده‌اند، به
همه‌جا اثر دارند، و «چیزی لازم نیست» دربارهٔ آن‌ها دروغِ آرام است.

### کشفِ خودکار

```bash
userbug map myapp --headed
```

خودش می‌گردد و نقشهٔ حالت‌ها را می‌سازد. `--headed` یعنی می‌بینیدش. و
حینش می‌توانید حرف بزنید:

```
n این مودال با Escape بسته نمی‌شود    یادداشت → یافته، با مسیرِ همان لحظه
w                                     الان کجاست؟
q                                     بس است — تمیز بایست
```

`q` قطعِ فوری نیست: خزش ممکن است وسطِ رندر باشد، پس در نخستین مرزِ امن
می‌ایستد و هرچه پیدا شده می‌ماند.

### شناختِ اپ

```bash
userbug learn myapp          # سورس را می‌خوانَد
userbug knowledge myapp      # چه می‌دانیم، و هر بند از کجا آمده
userbug capabilities myapp   # «این اپ چه دارد؟»
userbug coverage myapp       # «چه چیزی در سورس هست و صدایش نزده‌ایم»
```

هر بندِ شناخت با `by:` می‌گوید منبعش چه بوده — گشت، خزش، سورس، یا حرفِ
خودتان. حرفِ شما بر حدسِ ماشین می‌چربد.

### فایل‌های نمونه

```bash
userbug fixtures myapp --add ./نمونه.pdf --note "برای آزمونِ آپلودِ تکراری"
```

تستِ آپلود از همین‌جا می‌خوانَد، نه از هر جای دیسک:

```js
await page.getByLabel('فایل').setInputFiles(await ub.fixture('نمونه.pdf'));
```

## وقتی چیزی شکست

```bash
npx playwright show-trace test-results/<نام>/trace.zip
```

اسنپ‌شاتِ DOM در هر قدم، نتورک، کنسول. و چون `ub.step()` مرزِ زمانی
گذاشته، لاگِ سرور کنارِ همان قدمی می‌نشیند که شکست.

## چند نکته که وقت‌تان را می‌گیرند اگر ندانید

**فارسی در ترمینال.** `cmd.exe` فارسی را جدا و وارونه نشان می‌دهد حتی با
`chcp 65001`. **Windows Terminal** درست نشان می‌دهد. اگر خروجی به‌هم‌ریخته
دیدید، اول ترمینال را عوض کنید نه کانفیگ را.

**اپ باید بالا باشد.** userbug بالا نمی‌آوردش. اگر تست‌ها با
`ERR_CONNECTION_REFUSED` شکستند، اپ خاموش است.

**تستِ تازه ادعا ندارد، و این عمدی است.** کاوشگر نمی‌داند چه چیزی *باید*
می‌شد؛ ادعای حدسی یعنی باگِ امروز به‌عنوان «انتظارِ درست» رسمی شود.

**هزینهٔ مدل یک بار است.** `author` و `expect` و `learn` پول می‌گیرند.
`npx playwright test` رایگان است و هر بار که کد عوض شد اجرایش می‌کنید.

## چه چیزی هنوز نیست

`userbug quest` — کاوشِ هدف‌دار با مدل («برو ببین آپلودِ تکراری چه
می‌کند») — بسته است. قلبش با برداشتنِ اجرای YAML رفت و بازنویسی‌اش کارِ
مستقلی است. تا آن روز، `map` برای کشف و `tour` برای مسیرهای دقیق.
